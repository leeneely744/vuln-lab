# コメント機能の格納型XSS

対象: `GET /comments`(一覧表示)、`POST /comments`(投稿)

## Build(脆弱にした実装)

- `src/routes/comments.ts` の `GET /` で、DBから取得した`comments`をそのまま`comments.ejs`に渡している
- `src/views/comments.ejs` で `item.author` / `item.body` を `<%- %>`(エスケープなし出力)でレンダリングしている

## Attack

**ペイロード**

```
<script>alert(1)</script>
```

**結果**

コメント投稿フォームの入力に投入したところ、投稿直後にブラウザで`alert(1)`が発生した。さらにページをリロードしても再度アラートが発生することを確認した。

**反射型XSS(検索機能)との違い**

反射型はリクエストのたびに`q`をそのまま返すだけだったが、格納型はペイロードがDB(`comments`テーブル)に保存されるため、**そのページを開いた全ての閲覧者に影響する**。自分がリクエストを送ったときだけでなく、他ユーザーが`/comments`を開くだけで攻撃が成立する点が反射型より深刻。

## SQLi(書き込み経路)の調査結果: 対象外

`POST /comments`の実装(`db.prepare("INSERT INTO comments(author, body) VALUES (?, ?);").run(author, body)`)は、最初から`?`プレースホルダでバインドパラメータ化されていたため、投稿フォームにシングルクォート(`'`)を入力しても正常に投稿できた(エラーにならない)。

仕様書では当初この機能をSQLiの入力点として想定していたが、実装時点で既に安全な書き方になっていたため、SQLiは再現されなかった。検索機能(`SELECT`)で見た文字列結合の危険性と、プレースホルダ化による対策効果の違いを、期せずして実地で比較できた形になる。

## 原因(格納型XSS)

- DBから取得した値をHTMLエスケープせずに`<%- %>`で出力しているため、保存された`<script>`タグがブラウザにそのままHTML要素として解釈される
- 反射型と根本原因(出力時のエスケープ不備)は同じだが、攻撃者の入力が経由する場所(リクエストパラメータ vs DB)が異なる
