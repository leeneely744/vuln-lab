# コメント削除のCSRF

対象: `POST /comments/:id/delete`

## Build(脆弱にした実装)

- `src/routes/comments.ts` の削除エンドポイントには、CSRFトークンの発行・検証や、リクエスト元(Origin/Referer)のチェックが一切ない
- `req.params.id` を受け取ってそのまま`DELETE FROM comments WHERE id = ?`を実行するだけの実装

## Attack

**PoC**: [csrf_poc.html](./csrf_poc.html)

`vuln-lab`とは別のページとして用意した攻撃者ページ。中身は`http://localhost:3000/comments/1/delete`宛のPOSTフォームを1つ持ち、`window.onload`で自動的に送信ボタンをクリックする(ページを開いた瞬間に自動送信される)。

**手順と結果**

1. `vuln-lab`のサーバーを起動したまま、`csrf_poc.html`を`file://`から直接(ダブルクリックで)開いた
2. `localhost:3000/comments`を一度も直接開いていないにもかかわらず、対象コメント(id=1)が削除された
3. フォーム送信が通常のページ遷移として行われ、かつ`comments.ts`側の削除処理後に`res.redirect("/comments")`しているため、`csrf_poc.html`を開いた直後にブラウザが`/comments`(削除後の一覧)へ自動的に遷移した

**補足: ページ遷移について**

`fetch`のようなAPI経由ではなく通常の`<form>`送信を使っているため、リクエスト成功後にブラウザの表示ページが切り替わる。これはCSRFの成立可否には影響しない(攻撃者が狙った状態変更は既にリクエストの時点で完了している)。実際の攻撃では被害者に気づかれないよう、フォームを非表示のiframe内に置いて送信するのが定石だが、今回は未実施。

## 原因

- ブラウザは仕様上、**別オリジンのページからのフォーム送信(POSTを含む)をデフォルトで許可する**。同一オリジンポリシーは「レスポンスの読み取り」を制限するものであり、「リクエストの送信」自体は制限しない。これがCSRFという攻撃クラスが成立する根本の仕組み
- サーバー側がCSRFトークンなど「このリクエストが自サイトの正規のフォームから送信されたものか」を検証する仕組みを持っていないため、任意の外部ページから偽装されたリクエストをそのまま受理してしまう

## 補足: 認証なしでのCSRFの意味合い

v1では認証・セッション管理を実装していないため、今回のCSRFは「特定ユーザーのセッションを乗っ取って本人になりすます」という本来のCSRFの深刻さまでは再現できていない。ここで確認できたのは「外部サイトを訪問しただけで、アプリの状態変更(今回は削除)が訪問者のブラウザ経由で無関係に実行されてしまう」という核心のメカニズムのみ。v2でログイン機能を実装した後、認証済みセッションに対して同様の攻撃を試すと、より実害の大きいCSRFを再現できる見込み。

## Fix

ログイン機能がなくセッション管理も未実装(v2で対応予定)のため、セッションに紐づけるのではなく**サーバー側のモジュールスコープ変数にトークンを1つだけ保持する**簡易な方式で実装した。

- `crypto.randomBytes(16).toString('hex')` で推測不可能なトークンを生成し、`GET /comments`(一覧表示)のたびに再発行してモジュールスコープの変数を更新
- `comments.ejs`の削除フォームに、そのトークンを隠しフィールド(`<input type="hidden" name="token">`)として埋め込み
- `POST /comments/:id/delete`で、送られてきたトークンとサーバー側で保持しているトークンを比較し、不一致なら`403`を返して処理を中断

**確認**

- 正規の手順(`/comments`を開いてから削除ボタンを押す)ではトークンが一致し、削除処理が実行されることを確認
- `csrf_poc.html`(トークンを持たない偽装フォーム)では `403 Forbidden` が即座に返り、削除が実行されないことを確認

**実装時に見つかった副次的なバグ**

初回実装ではトークン不一致時に`return;`だけでレスポンスを返しておらず、リクエストがタイムアウトするまでハングする不具合があった(`curl`で無応答を確認)。`res.status(403)`で明示的にレスポンスを返すよう修正した。これはCSRF対策そのものとは別の、Expressのレスポンス処理忘れという一般的な実装ミスだった。

**制限事項**

- トークンをグローバルな単一変数で保持しているため、複数人が同時に使う実運用には向かない(今回は学習用のシングルユーザー前提として許容)
- `POST /comments`(新規投稿)にはCSRFトークンを付けていない。今回のスコープは削除エンドポイントのみを対象としたため

**余談: `res.status(403).end()`だけでは処理が止まらない**

脆弱性そのものとは無関係だが、実装中にNode.js/Expressの挙動として発見した点。`res.status(403).end();`はあくまで「レスポンスを送信する」という副作用を起こす呼び出しであって、JavaScript関数の実行フローを止める制御構文ではない。これだけを書いて`return;`を省略すると、その後に書かれた処理(今回で言えば削除処理や別の`res`呼び出し)がそのまま実行され続けてしまう。

レスポンス送信後にさらに別のレスポンス送信処理(`res.redirect()`など)まで実行されると、`Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client`というエラーになる。`res.status(403).end()`の直後に明示的に`return;`を書き、関数の実行をそこで止める必要がある。
