# パスワードの平文保存

対象: `users`テーブル、`POST /auth/login`

## Build(脆弱にした実装)

- `src/db.ts` で `users` テーブルの `password` カラムに、ハッシュ化せず入力値をそのまま保存
- `src/routes/auth.ts` のログイン処理も `SELECT * FROM users WHERE username = ? AND password = ?;` と、平文同士を直接比較する実装

## Attack

`sqlite3` CLIで`data/app.db`を直接クエリ:

```
sqlite3 data/app.db "SELECT * FROM users;"
```

**結果**

`password`カラムがハッシュ化されておらず、生のパスワード文字列がそのまま確認できた。加えて、シードデータの3ユーザー(Alice, Bob, Charlie)が全員同じパスワードを使い回していることも、DBを見ただけで一目瞭然だった。

## 原因

- パスワードを保存する際にハッシュ関数(bcrypt等)を通していない
- ハッシュ化されていれば、DBの中身が漏洩しても攻撃者が得られるのはハッシュ値のみで、元のパスワードを得るには追加の計算コスト(クラック)が必要になる。平文保存では、DBへの読み取りアクセスを得た時点で**即座に全アカウントへログイン可能な状態**になる

## 考察: 他の脆弱性との組み合わせ

今回はDBファイルに直接アクセスできる前提(ローカル環境)で確認したが、v1で見つけた検索機能のSQLi(修正済み)がもし残っていれば、DBへの直接アクセス手段がなくても、ブラウザ経由のUNIONベースSQLiだけで`users`テーブルのパスワードを丸ごと抜き出せていたはずである。単体の脆弱性でも危険だが、複数の脆弱性が組み合わさることで被害範囲がさらに拡大する典型例と言える。

## Fix

パスワードを`bcryptjs`でハッシュ化して保存し、ログイン時は`bcrypt.compare`で照合する形に変更した。

- `src/session.ts` に `hashPassword`(`bcrypt.hash`、cost=10)と `verifyPassword`(`bcrypt.compare`)を追加
- `src/db.ts` のシードデータを、ハッシュ化したパスワードで投入するよう変更(3ユーザーそれぞれ別のパスワードに変更)
- `src/routes/auth.ts` のログイン処理を「`username`だけで`users`から1行取得 → 行がなければ失敗 → `verifyPassword`で照合」の流れに変更
- `username`・`password`が文字列でない場合(未送信・配列・オブジェクト)はログイン失敗としてリダイレクトする型ガードを追加

**検討経緯: SHA-256ではなくbcryptを選んだ理由**

最初は`crypto.createHash("sha256")`でハッシュ化する実装を書いたが、パスワード保存には向かないため採用しなかった。

- **ソルトがない**: 同じパスワードからは常に同じハッシュ値ができる。今回のように全員が同じパスワードを使っていれば、ハッシュ化してもDB上で使い回しが一目でわかる。事前計算済みのハッシュ表(レインボーテーブル)で元の値を引くこともできる
- **計算が速すぎる**: SHA-256はもともと高速に計算できるよう設計されており、GPUなら毎秒数十億回試せる。総当たりで解読されやすい

bcryptは、ハッシュ化のたびにランダムなソルトを自動生成してハッシュ値の中に埋め込み、cost(2^cost回の繰り返し)によって意図的に計算を遅くしている。アルゴリズムが公開されていること自体は問題ではない。

**bcryptでは「ハッシュ同士をSQLで比較する」ことができない**

SHA-256のように「入力値をハッシュ化して `WHERE password = ?` で一致を探す」方式は、bcryptでは成立しない。ソルトが毎回ランダムなので、同じパスワードでもハッシュ化するたびに結果が変わるためである。そのため、まず`username`で行を取得し、保存済みハッシュに埋め込まれたソルトとcostを使って`bcrypt.compare`で照合する必要がある。

**確認**

`sqlite3 -box data/app.db "SELECT * FROM users;"` の結果:

```
┌────┬──────────┬──────────────────────────────────────────────────────────────┐
│ id │ username │                           password                           │
├────┼──────────┼──────────────────────────────────────────────────────────────┤
│ 1  │ Alice    │ $2b$10$mnKJEndxFEQAzYAV2VhFUu2l8rhd73ssZvM/LOnyHpcqoruCL/BC. │
│ 2  │ Bob      │ $2b$10$3FeRVLE.gP5z9niSxNrO7uNODr304MOAHF/3ONlfW3QaBWms2KHDG │
│ 3  │ Charlie  │ $2b$10$e9sNa6V5xaKZucp8g4v1LOchuXjRX7jKRO.skraNOCWa3FTK2KcPS │
└────┴──────────┴──────────────────────────────────────────────────────────────┘
```

`$2b$`がbcryptの形式、`10`がcost、続く22文字がソルト、残り31文字がハッシュ本体。DBを読まれても元のパスワードは直接わからない。また、ソルトがハッシュ化のたびにランダムに生成されるので、複数のユーザーが同じパスワードを使っていてもハッシュ値はユーザーごとに異なる。平文保存のときのように、使い回しがDBを見ただけでわかることはない(ただし、`hashPassword`を1回だけ呼んだ結果を全員に使い回すと同じ値になるので、ユーザーごとに呼ぶ必要がある)。

`curl`で`POST /auth/login`に各パターンを送った結果:

| 入力 | 結果 |
|---|---|
| 正しいusername・password | `/comments`へリダイレクト、セッションCookie発行 |
| パスワード誤り | `/auth/login`へリダイレクト |
| 存在しないusername | `/auth/login`へリダイレクト |
| password未送信・配列 | `/auth/login`へリダイレクト |
| username未送信・配列・オブジェクト | `/auth/login`へリダイレクト |

**実装時に見つかった副次的なバグ**

- **Promiseがそのまま保存された**: `hashPassword`は`async`関数なのに`await`せずにテンプレート文字列へ埋め込んだため、`password`列に文字列`[object Promise]`が保存された。INSERT自体は成功するのでその場では気づけず、ログイン時に初めて発覚した。ログイン処理側でも同じく`await`し忘れていたが、こちらはbetter-sqlite3がPromiseをバインドできず`TypeError`になったので気づけた。**プレースホルダ経由で値を渡していれば、壊れたデータは保存される前に止まる**。SQLi対策と同じ書き方がデータ破損の防止にもなる
- **`username`が配列だとログインできた**: 型ガードを最初は`password`にだけ入れていた。そのため`username[]=Alice&password=1234`を送るとログインに成功した。better-sqlite3は配列を「位置パラメータの並び」として解釈するので、`['Alice']`が`'Alice'`としてバインドされる。さらにセッションには文字列ではなく配列が保存されていた(`req.body`がany型のため、`Map<string, string>`の型宣言はこれを検出できない)。オブジェクト(`username[a]=Alice`)の場合は名前付きパラメータとして解釈されて例外になり、500が返った。**パラメータ化クエリでSQLiは防げても、入力の型を検証しないとライブラリ側の解釈で想定外の動きをする**。`express.urlencoded({ extended: true })`では、フォームデータから配列やオブジェクトを簡単に作れる点にも注意が必要
- **リダイレクト後に処理が止まらない**: ユーザーが存在しない場合に`res.redirect()`だけを書いて`return;`を忘れていた。そのため後続の`user.password`の読み取りまで処理が進んでいた(doc 04の余談と同じ種類のミス)。TypeScriptは`return`を書くまで`user`の型を`undefined`の可能性ありのまま扱い、`user.password`の参照をエラーにしていた。結果的にこの実行時バグを型チェックが検出していたことになる

**制限事項**

- シードデータのINSERTは、ハッシュ値をテンプレート文字列で埋め込む形のまま(値はアプリ内部で生成したもので、外部入力ではない)
- ユーザーが存在しない場合は`bcrypt.compare`を呼ばずに返すため、存在する場合より応答が速い。応答時間の差から、どのユーザー名が存在するかを推測できる可能性がある(タイミング攻撃によるユーザー列挙)。今回は未対策
- セッションIDの生成方法(`mySessions.size`の連番)やCookie属性など、セッション管理側の問題は別の題材として扱う
