# 推測可能なセッションIDによるセッションハイジャック

対象: `src/routes/auth.ts` のログイン処理、`mySessions`(`src/session.ts`)

## Build(脆弱にした実装)

ログイン成功時に、その時点のセッション数 `mySessions.size` を文字列化した値をセッションIDとして払い出していた。

- `const sessionId = String(mySessions.size);`
- ログインした順に `0`, `1`, `2`, ... と連番が振られる
- サーバーは、Cookie の `sessionId` が `mySessions` に登録されていればログイン済みユーザーとみなす。つまりセッションIDを知っていることがログイン済みの唯一の証明であり、パスワード同様に秘密であるべき値が推測可能になっていた

## Attack

2つのブラウザ(Chrome=Alice、Firefox=Bob)でそれぞれログインし、開発者ツールの Cookie ストレージで `sessionId` を確認した。

- Alice: `sessionId=0`
- Bob: `sessionId=1`

Bob のブラウザの Cookie を `1` から `0` に書き換え、`/comments` を再読み込みしたところ、**Alice のパスワードを一切知らないにもかかわらず、コメント一覧が Alice のもの(author による絞り込み結果)に変わった**。Bob は Alice になりすませた。

必要だったのは「自分のIDが `1` なら、その1つ前は `0`」という推測だけである。bcrypt でパスワードをどれだけ強固に守っても、ログイン後の入口がこれでは意味がない。

## 原因

セッションIDに求められる要件(徳丸本 4.6)のうち「推測困難であること」が破れていた。

- 連番は、自分が払い出された番号の前後を数個試すだけで他人のセッションIDに到達できる
- 加えて `mySessions.size` を採番に使っていたため、ログアウトで件数が減ると番号が重複し、既存セッションを上書きしてしまう二次バグもあった(攻撃以前に、通常利用で他人として扱われうる)

## Fix

セッションIDの採番を `crypto.randomUUID()` に変更した。

- `String(mySessions.size)` をやめ、暗号的に安全な乱数から生成される UUID v4 を払い出す
- `mySessions.size` に依存しなくなったため、ログアウト時の番号重複による上書きバグも同時に解消した
- `crypto` は Node.js のグローバルとして利用可能(import 不要)

**確認**

ログイン後に払い出された Alice のセッションIDは `bd24a997-5cd5-484e-b774-059bbbdea468` だった。

- 36文字(ハイフン4つ込み)の UUID v4 形式。3ブロック目が `4` で始まるのがバージョン4(乱数ベース)の印、4ブロック目が `8`〜`b` で始まるのが variant ビット。固定数ビットを除く **122ビットが乱数**
- 連番の `0` のような「隣の値」が存在せず、自分のIDから他人のIDを導く手がかりがない。前回の「前後を試す」攻撃は成立しなくなった

## 制限事項(このFixで直らない点)

`randomUUID()` は「推測困難」のみを解決する。セッションIDに求められる他の要件は別途対応が必要で、今回は未対策:

- **有効期限がない**: 払い出したIDはログアウトするまで永久に有効。発行時刻を保持し、一定時間経過で無効化する仕組みが必要
- **Cookie 属性が未設定**: HttpOnly・Secure・SameSite が付いていない。セッションIDを「推測する」経路は塞いだが、XSS などで「盗む」経路は残っている(次の題材)
- **ログイン時の再発行(セッション固定対策)**: 今回は「ログイン時に初めて発行する」作りのため、この要件は結果的に満たしている

実運用では自前実装ではなく `express-session` などの実績あるライブラリに任せるのが一般的。乱数ID・有効期限・Cookie 属性をまとめて扱える。vuln-lab では「自分で作って壊れ方を理解する → 本番でライブラリに任せる理由がわかる」順序に意味がある。
